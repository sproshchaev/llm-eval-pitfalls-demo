# llm-eval-pitfalls-demo

[![check](https://github.com/sproshchaev/llm-eval-pitfalls-demo/actions/workflows/check.yml/badge.svg)](https://github.com/sproshchaev/llm-eval-pitfalls-demo/actions/workflows/check.yml)
[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](LICENSE)

Учебный эксперимент к статье на Хабре
«[Тестирование LLM-фичи: 7 ошибок, из-за которых eval зелёный, а в проде бред](https://habr.com/ru/companies/otus/articles/1088876/)».

Одни и те же записанные ответы AI-ассистента поддержки оцениваются четырьмя способами.
Общий балл 96% и порог 95% говорят «можно выпускать». Остальные три отчёта по тем же
данным говорят, что нельзя.

## Быстрый старт

Нужен только `python3`, сторонние пакеты не используются. Живая модель и ключи API не нужны:
ответы уже записаны в `data/`.

```bash
git clone https://github.com/sproshchaev/llm-eval-pitfalls-demo.git
cd llm-eval-pitfalls-demo
./run.sh
```

`run.sh` пересобирает данные генератором, проверяет, что они совпадают с `data/` байт в байт,
печатает отчёты и сверяет вывод с `expected.txt`.

Гейт для CI с кодом выхода 1 при нарушении жёсткого инварианта:

```bash
python3 eval.py --strict
```

## Результат

**1. Общий балл и категории.** 1018 верных прогонов из 1060, то есть 96,0%.

| Категория | Корректность | Прогонов |
|---|---:|---:|
| типовые вопросы (`typical`) | 99,5% | 600 |
| возвраты и деньги (`refunds`) | 98,0% | 200 |
| персональные данные (`personal_data`) | 100,0% | 100 |
| вопросы вне темы (`out_of_scope`) | 73,3% | 60 |
| редкие формулировки (`rare_wording`) | 81,0% | 100 |

Типовых вопросов больше всего, и они тянут среднее вверх. Вопросы вне темы и редкие
формулировки дают 35 неверных прогонов из 42, но в общем балле этого не видно.

**2. Гейт.** Корректность 96,0% проходит порог 95%. Но в двух прогонах ассистент пообещал
возврат денег сверх политики (`promise_beyond_policy`). Это жёсткий инвариант: в тестовом
наборе не должно быть ни одного наблюдаемого нарушения, поэтому итог гейта — FAIL. Ноль
наблюдаемых нарушений не доказывает, что их не будет в проде: жёсткие инварианты держатся
ещё и проверками в самом приложении, а не только eval. В другом прогоне того же кейса ответ был верным:
одиночный тест эту ошибку легко пропустил бы.

**3. LLM-судья.** На 200 размеченных ответах с 26 нарушениями:

| Показатель | Значение |
|---|---:|
| доля совпадений с людьми | 97,0% |
| precision | 95,5% |
| recall | 80,8% (пропущено 5 из 26) |
| recall, 95% интервал Уилсона | 62,1–91,5% |
| судья «всегда нет», для сравнения | совпадение 87,0%, recall 0% |

Высокая доля совпадений скрывает, что на этой выборке судья пропустил почти каждое пятое
нарушение. Даже судья, который вообще ничего не проверяет, совпал бы с людьми в 87% случаев.
Интервал показывает и обратное: 26 нарушений — мало для уверенного вывода о судье вообще,
выборку нужно расширять.

**4. Рабочий набор против отложенной выборки.** После правок промпта, сделанных с оглядкой
на рабочий набор, на нём 98%. На отложенной выборке (holdout), которая не использовалась при настройке, — 85%.
Разница в 13 пунктов — это подгонка, а не качество.

## Границы применимости

- Данные синтетические. Состав задан в `generate_data.py` явно, чтобы цифры совпадали со
  статьёй. Это иллюстрация механики измерения, а не замер конкретной модели.
- Ручная разметка и вердикты судьи записаны готовыми полями. Как получать их на своих данных
  (кто размечает, какой судья, какие критерии), разобрано в статье.
- Пороги 95% и нулевой допуск по инвариантам — пример. Реальные пороги задаёт владелец
  продукта.

## Структура

| Файл | Что внутри |
|---|---|
| `data/runs.jsonl` | регрессионный набор: 106 кейсов по 10 прогонов, категория, ответ, ручная разметка, вид нарушения |
| `data/judge_sample.jsonl` | 200 ответов с ручной разметкой и вердиктом LLM-судьи |
| `data/tuning.jsonl` | рабочий набор и отложенная выборка по 100 ответов |
| `generate_data.py` | генератор данных с фиксированным seed |
| `eval.py` | четыре отчёта и гейт `--strict` |
| `expected.txt` | эталонный вывод `eval.py` |
| `run.sh` | проверка воспроизводимости данных и вывода |
| `.github/workflows/check.yml` | то же в CI, плюс проверка, что гейт падает |
